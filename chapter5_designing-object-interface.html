    Section 5.8 Designing an Object’s Interface and Behavior

    A class is more than a collection of private data members. Its public member functions describe how other code is allowed to interact with its objects.
    🔗
    The public part of a class forms its interface. The operations provided by that interface describe the object’s behavior.
    🔗
    Good class design therefore asks two related questions:
    🔗
    • What should code outside the class be allowed to do?
      🔗
      🔗
    • Which operations naturally belong to the object itself?
      🔗
      🔗

    Subsection 5.8.1 The Public Interface

    Consider a simple Thermostat class:
    🔗
    class Thermostat {
public:
    Thermostat(double initial_temperature);

    double get_temperature() const;
    bool set_temperature(double new_temperature);

private:
    double temperature;
};
    Code outside the class can see and use the public constructor and member functions. It cannot directly access temperature.
    🔗
    This means the public interface communicates the intended ways to use a Thermostat:
    🔗
    Thermostat room{21.0};

double current = room.get_temperature();
bool changed = room.set_temperature(23.0);
    The private representation is an implementation detail. Code using the class should depend on the public interface rather than on how the object stores its state.
    🔗
    🔗

    Subsection 5.8.2 Observer Functions

    A member function that reports information about an object without changing it is often called an observer.
    🔗
    double Thermostat::get_temperature() const {
    return temperature;
}
    Because this function only observes the object, it is declared const.
    🔗
    A function whose main purpose is to return one particular data value is often called a getter or accessor. The name get_temperature makes that purpose clear.
    🔗
    However, private data does not mean that every data member automatically needs a getter. A public operation should exist because outside code has a meaningful reason to use it.
    🔗
    Sometimes an observer reports information derived from the object’s state instead of returning a stored value directly:
    🔗
    class Rectangle {
public:
    double calculate_area() const;

private:
    double length;
    double width;
};
    Here, calculate_area() is part of the useful interface even though there is no data member named area.
    🔗
    🔗

    Subsection 5.8.3 State-Changing Functions

    Other member functions intentionally change an object’s state. These functions do not have a trailing const.
    🔗
    bool Thermostat::set_temperature(double new_temperature) {
    if (new_temperature < 10.0 || new_temperature > 30.0) {
        return false;
    }

    temperature = new_temperature;
    return true;
}
    In this example, our Thermostat model accepts settings from 10 through 30 degrees. The member function checks the requested value before changing the private data.
    🔗
    The return value tells the caller whether the requested change succeeded:
    🔗
    bool changed = room.set_temperature(35.0);
    Since 35.0 is outside the range chosen for this model, changed is false and the object’s previous temperature is preserved.
    🔗
    A state-changing member function is often called a setter or mutator. As with getters, the important design question is not whether a setter can be written, but whether the operation belongs in the object’s public interface.
    🔗
    🔗

    Subsection 5.8.4 Prefer Meaningful Behavior When Possible

    A public interface often becomes clearer when its member functions describe meaningful actions rather than simply exposing every piece of stored data.
    🔗
    For example, suppose a BankAccount stores a balance. A design could provide:
    🔗
    bool set_balance(double new_balance);
    But an interface based on the actions that accounts actually perform may communicate the design better:
    🔗
    void deposit(double amount);
bool withdraw(double amount);
double get_balance() const;
    The second design describes behavior: money can be deposited or withdrawn, and the balance can be observed. Outside code does not need permission to replace the balance with an arbitrary value.
    🔗
    This does not mean that setter functions are always wrong. A setter is useful when directly replacing a property is itself a meaningful operation. The goal is to make the interface express the intended use of the object.
    🔗
    🔗

    Subsection 5.8.5 Keep the Interface Focused

    Making a member function public means that other code is invited to depend on it. A good interface therefore provides the operations that users of the object need without exposing unnecessary details.
    🔗
    Compare these two designs:
    🔗
    class Rectangle {
public:
    double get_length() const;
    double get_width() const;
    void set_length(double new_length);
    void set_width(double new_width);
    double calculate_area() const;

private:
    double length;
    double width;
};
    and:
    🔗
    class Rectangle {
public:
    bool set_dimensions(double new_length, double new_width);
    double calculate_area() const;

private:
    double length;
    double width;
};
    Neither interface is automatically correct for every program. If outside code genuinely needs to inspect or replace each dimension separately, the first design may be appropriate. If dimensions should normally be changed together, the second interface may better express that design.
    🔗
    The important idea is that public functions should be chosen deliberately rather than generated mechanically for every private data member.
    🔗
    🔗

    Subsection 5.8.6 Member Function or Free Function?

    Not every useful operation involving an object needs to be a member function. Free functions remain an important part of C++.
    🔗
    A useful question is:
    🔗
    Does this operation naturally belong to this object?
    🔗
    🔗
    An operation is often a good member function when it:
    🔗
    • observes the state of one object,
      🔗
      🔗
    • changes the state of one object, or
      🔗
      🔗
    • represents behavior that is naturally associated with that type.
      🔗
      🔗
    For example:
    🔗
    room.calculate_area();
account.deposit(50.0);
thermostat.set_temperature(22.0);
    A free function can be a better choice when the operation is more general and does not naturally belong to one particular object.
    🔗
    double calculate_distance(const Point& first, const Point& second);
    The distance describes a relationship between two points. It does not need to be treated as a behavior owned by either point.
    🔗
    These are design guidelines rather than rigid rules. As programs become larger, choosing clear responsibilities becomes an important part of program design.
    🔗
    🔗

    Subsection 5.8.8 Check Your Understanding

    Checkpoint 5.8.1.

    Which member function should normally be declared const?
    🔗
    • double get_temperature() const;
    • This function observes the object without changing its state.
    • bool set_temperature(double new_temperature);
    • This function may change the object’s state, so it should not be a const member function.
    • void deposit(double amount);
    • A deposit changes the account’s state.
    🔗

    Checkpoint 5.8.2.

    Which interface best expresses the behavior of a bank account?
    🔗
    • Only set_balance(double new_balance)
    • Replacing the balance directly does not express the usual actions performed on an account.
    • deposit, withdraw, and get_balance
    • These operations describe meaningful account behavior while keeping direct control of the stored balance inside the class.
    • Make balance public and provide no member functions.
    • That gives outside code unrestricted access instead of defining a controlled interface.
    🔗

    Checkpoint 5.8.3.

    Which operation is a strong candidate for a free function rather than a member function?
    🔗
    • Depositing money into one BankAccount
    • A deposit changes the state of one account and naturally belongs to that object.
    • Reading one Thermostat’s temperature
    • Observing the state of one thermostat naturally fits its public interface.
    • Calculating the distance between two Point objects
    • Distance describes a relationship between two points and does not have to belong to either point.
    🔗

    Checkpoint 5.8.4.

    Why should a class not automatically provide a getter and setter for every private data member?
    🔗
    • Because C++ does not allow getters and setters for private data.
    • Public member functions can read or modify private data members.
    • The public interface should expose operations that are meaningful for using the object, rather than exposing internal state mechanically.
    • A focused interface communicates how the object is intended to be used.
    • Because every private data member must remain permanently unchanged.
    • Private members can be changed by the class’s own state-changing member functions.
    🔗
